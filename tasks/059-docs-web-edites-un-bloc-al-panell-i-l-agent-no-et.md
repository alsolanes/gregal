## Why

A live document has to be editable by the person too, while the agent keeps working, without closing anything or losing what was just typed. Edits go block by block, and a block the person has just changed must not be overwritten by an agent that has not read it.

## Acceptance criteria

- [x] `PUT /api/docs/{id}/blocks/{block}` `{md, base_version}` replaces a block as `author: user`; `POST /api/docs/{id}/blocks` `{after, md}` inserts and `DELETE /api/docs/{id}/blocks/{block}` deletes. A `base_version` older than the block's current version returns 409 with the current block. A Go test of each route, of the 409, and that every open stream receives the change.
- [x] The `doc` tool's `replace` and `delete` fail with an error that tells the agent to read the block again when the person changed that block after the agent last read or wrote it; edits to blocks the person has not touched still apply. A Go test: agent reads, user replaces block 2, agent replace of block 2 fails with that error, agent replace of block 3 succeeds, agent reads again and then replaces block 2.
- [x] In the panel, clicking a block turns it into a text area with its markdown in place; leaving it or Ctrl+Enter saves, Esc cancels, Enter at the end of the last line inserts a new block below, and emptying a block and saving deletes it. On a 409 the panel shows the current text and a notice «L'agent ha canviat aquest bloc» / «The agent changed this block» and keeps the person's text to copy. A node test of the editing state machine (open, save, cancel, insert, delete, conflict).
- [x] While the person edits a block, `block` events for that same block do not replace the text area; events for other blocks still apply. A node test.
- [x] `docs/api-contract.md` documents the three routes and the 409.

## Out of scope

- Rich in-place formatting (WYSIWYG toolbar): blocks are formatted when shown and edited as markdown.
- The per-turn summary to the agent (060), Android (063).

## Notes

- The agent's last-seen version per block can live in the store, keyed by session, since 060 needs the same record.
- Block ids are generated by the server; the client never invents them.
- Done: the guard lives in the store, inside the per-root lock: `Store.Replace` and `Store.Delete` take a `base` version and return `*gdocs.ConflictError{Block}` when the block changed after it. A person's edit conflicts with any later change of the block; an agent's edit only with a change by the person (agents may overwrite agents). The `doc` tool passes `Store.Seen(session)[id]` as base, so an agent that never read the document in this session must read it before replacing a block the person wrote. The 060 turn note also marks documents as seen, so after it the agent may edit the blocks it was told about.
- Routes: `POST /api/docs/{id}/blocks` → `{version, blocks}` (the new ones), `PUT …/blocks/{block}` → `{version, block}`, `DELETE …/blocks/{block}?base_version=N` → `{version}` (base in the query, required), 409 `{error, block}`. The client's `base_version` is the block's own `version`.
- Editing is in `doc-view.js` (`view(box, doc, render, edit)`; `edit` = `{put, post, del, notice, error}`), so 061 gets it by passing the same `blockEdits(id)` the panel builds in `docs-panel.js`. A new block has no id until the POST answers; the view applies the answer as `insert`s and ignores the stream's copy of the same insert. After a 409, leaving the text area does not save (only Ctrl+Enter overwrites, now against the version shown); Esc shows the current text.
- Not checked in a running browser: keys, blur and saving were tested with a fake DOM in node.
- Follow-up: clicking another block after a 409 closes the conflicted editor and drops the person's text; a stream reconnect (new view) also drops an open editor.
- Follow-up: the 409 notice always says the agent changed the block, even when it was the person in another tab.
- Follow-up: Android (063) and the other clients do not edit blocks yet.
